样稿使用合成数据。可以切换外观、筛选跑鞋、打开鞋详情及表单。关联活动行打开绑定预览，供审阅活动详情中的绑定控件；表单无持久化。

## 推荐方案

在本人的「跑步记录」工具栏增设「跑鞋」，在本人活动详情提供换绑和解绑。每条活动最多关联一双鞋。累计里程由服务端实时计算：初始里程加所有已绑定活动保存在 `activities.distance_m` 的距离。替换提醒按每双鞋自行设定的里程阈值计算，首版只在跑鞋页内显示。

| 方案 | UX 与数据结构 | 取舍 |
| --- | --- | --- |
| A · 跟随活动（推荐） | 跑步记录入口，详情绑定；活动持有可空 `shoe_id`，一对多，复合外键 `RESTRICT` | 导入后或回看历史时就近绑定；一条活动只有一个归属，查询与变更路径短；删鞋需先处理关联，账号删除需验证外键顺序 |
| B · 从账户设置管理鞋柜 | 设置里增「跑鞋」分区，鞋详情挑选记录；独立 `activity_shoes` 关联表，`UNIQUE(activity_id)`，两条带归属的复合外键 | 将来可为绑定保存来源、分段里程等独立字段；首版增加关联查询和生命周期选择，且入口远离导入与活动浏览 |
| C · 按鞋手工登记里程 | 在账户设置登记鞋，每次录入增量；独立里程流水 | 可录入系统外的运动；活动与鞋的数据会分离，同一活动产生双录风险，删除或修订活动时无法同步 |

## 使用流程

- **入口**。站主在本人 `/activities` 的工具栏打开 `/activities/shoes`，普通成员在 `/workspace/activities` 打开 `/workspace/activities/shoes`。两边复用界面与本人 API。页面明确要求有效本人会话，站主根路径另核对站主身份，普通成员的根路径访问可重定向到本人工作区。具名展示、匿名活动、跨用户管理员活动视图无入口；不能以 `viewsOwnRecords()` 单独决定可见性，因为该 helper 也覆盖自己的具名展示。
- **列表与详情**。默认「使用中」，另有「已退役」筛选；使用中先列已达阈值，再列接近阈值，其余按创建时间倒序，`id` 稳定打破并列。退役组按退役日期倒序。列表展示鞋名、选填品牌/型号、累计与阈值状态。≥1024px 左侧列表、右侧所选鞋详情，可将选中项写入 `?id=`；窄屏进入详情视图，返回恢复筛选与位置。详情突出累计，拆出初始里程和已绑活动里程，关联活动按日期倒序分页，显示日期、标题、距离和本人活动链接。网址无标题或备注。
- **添加与编辑**。用同一套原生表单，鞋名必填，品牌、型号、购入日、备注选填。初始里程默认 `0`，提醒阈值留空可关闭。初始里程旁保留一句说明「只填写尚未录入的里程。」新增成功选中该鞋；编辑成功更新列表和详情。详情提供明确标有「退役跑鞋」/「恢复使用」的操作，危险区提供无关联鞋的删除确认。
- **活动绑定**。本人活动详情的「跑鞋」行显示当前鞋名或「未绑定」。原生选择框列出使用中鞋并可选择「不绑定」，显式保存当前选择；存在退役关联时显示原鞋和「已退役」，可保留、换绑或解绑，退役鞋不作为新绑定候选。回填退役鞋的历史活动时，先恢复鞋再绑定，可随后再次退役。没有使用中的鞋时给「添加跑鞋」链接。导入成功可从既有回执打开活动详情后再绑定。
- **空、加载与错误**。初次进入用 `PageSkeleton`。无鞋用 `FeedbackState` 提供添加动作；分组为空分别显示「没有使用中的跑鞋」或「没有已退役的跑鞋」。详情无活动时保留初始里程并提供回活动列表的入口。刷新或筛选保留上次成功的数据；读取失败提供局部重试。保存/删除失败保留表单与当前绑定并就地提示；已有引用的删除回复提示先解绑或退役。401 清除鞋列表、绑定和草稿，跳登录；请求令牌与卸载清理防止过期数据回填。
- **设计系统与可访问性**。用 `PageHeader`、`.settings-tabs` 分段、既有 `.button-*`、`FeedbackState` 与长表单的 `SaveBar`；保持暖浅色/暖炭灰、24px 卡片、胶囊控件和等宽数字。主题使用站点现有偏好；手机保留文档流菜单和单列，触控目标至少 44px。状态同时有文字；进度视觉之外显示累计/阈值与状态，阈值关闭时省略进度。导航与列表用链接，筛选用 `aria-pressed`，表单有标签、错误关联、可见焦点，保存状态 `role=status`，错误 `role=alert`。测试 Tab、Escape、弹窗焦点恢复及 320px 长文本。

## 里程与提醒

`累计米数 = initial_distance_m + COALESCE(SUM(同一用户且 shoe_id 匹配的现存活动.distance_m), 0)`。活动计数用同一集合，0 米活动也计一次，里程加 0。GPX、TCX、小米运动健康与已有手动记录均按该口径；用户选择绑定即确认要计入，跑步之外的磨损也可由用户显式计入。日期、公开级别、路线是否存在、配速可用性和活动质量警告均不改变资格。购入日与退役日是鞋的描述性日期，不是距离查询边界。

初始里程只代表 RunNote 尚未记录的磨损，例如从旧平台带来的距离。补录同一批活动后需调低初始里程，系统无法推断重叠。解绑、换绑、单删/批删活动或未来距离更正后，下次读实时反映。退役记录保留原绑定并继续反映历史更正，恢复使用延续现有累计。两个来源的独立活动若仍被重复导入且都被绑定，按两条记录计入，沿用现有去重与修正行为。

阈值每双鞋自定义，留空关闭；字段示例 `800 km` 仅作为可编辑示例。`total >= threshold` 显示「已达替换里程」，`0.9 × threshold <= total < threshold` 显示「接近替换里程」及剩余量。阈值判断由服务端按原始米数完成，中文界面通常显示 1 位小数，临界点仍差少量时显示「不足 0.1 km」的剩余量，进度条视觉可封顶，累计数字展示实际值。退役鞋不提示，恢复后按当前数据派生提醒。里程可因绑定或删除回落，页面随之重算。首版不发推送、邮件、站内通知或后台定时任务，也不保存达到时间或已读状态。

合成样例「长距离训练鞋」初始 `120.0 km`，已经绑定的活动合计 `642.4 km`，累计 `762.4 km`。阈值 `800 km` 时显示「接近替换里程」，剩 `37.6 km`；解绑一条 `18.6 km` 活动后累计 `743.8 km`，仍接近阈值。

## 模型与私有接口

| 字段 | 建议 |
| --- | --- |
| `shoes.id`, `user_id` | UUID PK（`uuid4`）；`user_id NOT NULL` → `users.id ON DELETE CASCADE`；`UNIQUE(id,user_id)` 作为归属外键目标 |
| `name`, `brand`, `model`, `notes` | `name varchar(80)`，去空白后 1–80 字符。`brand/model varchar(60)`，`notes text` 上限 1000 字符；选填空值归一为 `NULL`，允许重名 |
| `purchased_on`, `retired_on` | `date NULL`；退役用请求时钟转换至账户时区写入当天，恢复置空。重复设置同一状态保持原日期。若两日期皆有值，校验退役日不早于购入日 |
| `initial_distance_m`, `replacement_distance_m` | `Numeric(12,3)`；初始值非空默认 `0`，阈值可空；具名 CHECK 分别要求 `[0, 1000000000)` 与 `(0, 1000000000)` 米。API 用严格十进制字符串验证精度、范围及有限性，UI 接受公里并精确转米。聚合返回精确十进制字符串且允许总数超出单笔上限 |
| `created_at`, `updated_at` | 时区感知时间戳，`server_default=func.now()`；与现有模型一致维护 `updated_at` |
| `activities.shoe_id` | 可空 UUID；`FOREIGN KEY (shoe_id,user_id) REFERENCES shoes (id,user_id) ON DELETE RESTRICT`。默认空关联，历史活动不回填 |

`shoes(user_id)` 供本人列表与账号删除定位；活动使用部分索引 `(user_id, shoe_id, activity_date DESC, id DESC) WHERE shoe_id IS NOT NULL`，同时支持归属外键查找、详情分页和聚合。列表先选同一用户当前页的鞋，再一次 `LEFT JOIN`/分组聚合这批鞋，或在需要按派生提醒排序时先对该用户的鞋做一次分组后排序分页；首版无缓存字段、触发器或双写计数。活动页与总计独立请求时允许并发更新造成短暂版本差异，鞋详情同一次响应需要一致值时用单语句或单一读取快照。

- 本人域建议 `GET/POST /api/v1/me/shoes`，`GET/PATCH/DELETE /api/v1/me/shoes/{identifier}`，`GET /api/v1/me/shoes/{identifier}/activities`，`GET/PATCH /api/v1/me/activities/{identifier}/shoe`。绑定 PATCH 的 `shoe_id: UUID | null` 字段必传，`null` 表示解绑；鞋 PATCH 按 `exclude_unset`，阈值可显式清空，退役状态使用布尔意图并由服务计算日期。列表按 `limit/offset`，相关活动接口使用明确字段白名单，仅含本人列表所需 ID、标题、日期、距离。选鞋按名称分页或搜索，不静默截断可选鞋。接口名和字段在确认后再定稿。
- 私有端点使用认证、`require_write` 的 CSRF/Origin 校验、统一 envelope 与 `StrictInput`，输入不接受任意 `user_id`，SQL 同时检查活动与鞋归属。无资源和跨用户同为 404；已有引用返回 409 `SHOE_IN_USE`，退役鞋的新增绑定返回 409 并保留原绑定。私有响应 `no-store`，前端校验响应结构；独立端点避免改变公共 API/schema、共用活动 DTO 与公开链接。鞋和绑定均不进入根/具名展示、摘要/令牌分享、海报、外部地图、公开日志、导出或 AI 上下文与供应商 payload。
- 写事务按现有 `lock_owner` 顺序获取用户行锁后读取/写入鞋及活动。同步服务 `flush`、路由 `commit`，绑定或鞋配置这类纯私人变动不递增 `activity_data_version`（沿用现有归属锁并记录这一设计选择），删除活动继续走原有版本处理。绑定/删除/退役并发由锁串行；FK 为额外防线，按具名约束映射冲突。重放同一绑定/退役请求不累加里程。不可硬删有引用的鞋，可先逐条解绑，退役保留历史。

## 迁移与验证草案

1. 当前仓库版本链末端是 `0030_global_footprint_caches`。实现前用 `alembic heads` 重查唯一 head 并与工作项 18 协调编号。若 head 未变，手写 `0031_shoes`，`down_revision = "0030_global_footprint_caches"`。若 0031 已由并行变更使用，顺延并保持线性链。
2. 建 `shoes` 表、完整命名约束及归属索引。给 `activities` 加可空 UUID 列，再建跨表复合外键与部分索引。现有行空值，无数据填充。大型实例测量 FK 校验与索引构建的锁等待和耗时；依据数据量评估是否需分阶段校验。数据库就绪接口以实际 head 为准。
3. **账号删除回归是合并门槛。** [现有批量删用户](../../../../backend/app/modules/admin_users/service.py) 按顺序锁账号后依赖数据库 cascade。现有 spike 没覆盖 `users` 同时级联删除 `shoes` 和 `activities` 触发 `RESTRICT` 的行为。推荐在同一批删事务、持有现有用户锁后，对确认待删用户的活动先将非空 `shoe_id` 置空，再执行既有用户删除；测试同批多个含鞋用户、站主保护及回滚。独立删鞋仍遵守 RESTRICT。
4. 降级先检查 `shoes` 有数据或 `activities.shoe_id` 非空即抛 `RuntimeError`，拒绝丢历史；空库依次移除活动部分索引、复合 FK 和列，再删鞋索引和表。在 `app/models/__init__.py` 注册模型，`app/main.py` 注册路由，生成私有 TS 契约；架构测试登记跨用户 404、公开字段隔离、严格输入和 CSRF，补合成 API 夹具。迁移编号、命名和防御性降级由已有守护覆盖。
5. 实现阶段只用允许名单内的隔离 `_test` PostgreSQL/PostGIS 库。跑完整 upgrade、已有活动保留空关联、空表 downgrade → upgrade、有数据拒绝 downgrade。真实库另测直接写入跨用户复合外键失败、被引用鞋删除失败、解绑后删除、身份和并发冲突、删除活动实时回算、账号级联。跑集成用例覆盖三类导入及补录、零米、已存在的 manual、换绑、批删、退役与阈值边界，以及带鞋活动的公开展示、分享和 AI 字段不泄漏。前端用合成 API 验证入口访问、绑定错误、401、各状态、主题、浏览器键盘和关键断点，真实后端 e2e 验证绑定与隔离。

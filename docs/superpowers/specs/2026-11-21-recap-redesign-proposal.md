# RunNote 月度 / 年度跑步回顾页与 9:16 分享图重设计提案

2026-11-21 · 基于 `origin/main`（`15b2090`，v1.3.0）· **设计提案与可交互原型阶段（未改动产品代码与迁移）**

---

## 一、现状审计：为什么当前版本显得“简陋、无聊、一般”

对照当前生产代码与已批准基线进行逐项审计：
- 页面与组件：[+page.svelte](../../../frontend/src/routes/workspace/records/recap/+page.svelte)、[RecapDistribution.svelte](../../../frontend/src/lib/components/RecapDistribution.svelte)、[RecapShare.svelte](../../../frontend/src/lib/components/RecapShare.svelte)、[recap.ts](../../../frontend/src/lib/recap.ts)
- 分享图渲染：[recap-render.ts](../../../frontend/src/lib/share/recap-render.ts)（仅 87 行）
- 功能文档与设计基线：[92-running-recap.md](../../92-running-recap.md)、`runnote-recap-design/design.md` 及对应 1440×900 / 390×844 / 1080×1920 样稿

当前版本在工程可用性、权限门控、隐私边界与一致性校验上非常扎实，但视觉体验和情绪价值偏弱，根因集中在 5 个方面：

| 维度 | 当前 v1.3.0 实际表现 | 问题本质 |
| --- | --- | --- |
| **1. 信息层级与页面节奏** | 全页只有两个堆叠圆角矩形：一个淡奶油黄方块（`.overview`）+ 一个白方块（`.distribution`）。 | 像“个人记录页的放大版卡片”，没有阅读的起承转合（定调 → 规模感 → 节奏起伏 → 坚持度与配速脉络 → 封存分享仪式），一眼看完且毫无记忆点。 |
| **2. 严重浪费已有服务端数据** | `GET /api/v1/statistics/trends` 的每个 `TrendBucket` 已继承 `Summary`，自带每期 `distance_m`、`activity_count`、`activity_days`、`duration_sum_seconds`、`avg_pace_seconds_per_km`；但 `recap.ts` 的 `buildRecap()` **丢弃了除 `distance_m` 外的所有字段**。 | 页面和分享图被迫只剩“单维度里程柱子”，看不到“哪个月配速最快”、“全年有几个月持续开跑”、“里程如何一路累积”，内容天然显得单薄。 |
| **3. 图形语言贫瘠且无交互** | `RecapDistribution.svelte` 是纯 CSS `div.bar` + 4 条 `repeating-linear-gradient` 横线，12 根绿柱子无点击/悬停联动、无数值反馈、无与跑步相关的视觉隐喻。 | 连站内既有的 `RecordsChart` 都已经去网格线并聚焦高光，Recap 反而退回为最普通的后台报表柱图。 |
| **4. 零动效与零触感反馈** | 进场、切周期、展开预览均为静态替换，没有数值递进、曲线生长、扇区扫过或触觉回弹。 | 缺少“拆开一份月度 / 年度封存纪念册”的仪式感。 |
| **5. 1080×1920 分享图毫无构图张力** | `recap-render.ts` 直接把网页上的黄框 + 12 根小柱子 + 4 个横线数字纵向摆进白底/炭灰底，底部大片留白、缺乏视觉焦点与图形钩子。 | 对比站内现有的单活动海报（`poster-sport.png` 的满版森绿英雄面与 `poster-ticket.png` 的实体票根），Recap 分享图反而最像“网页拉长截图”，难以激发发朋友圈/小红书/Story 的分享欲。 |

## 二、数据守恒、隐私边界与工作项 19 隔离

本次重设计**不新增任何后端 API、不修改数据库表结构与迁移、不编造任何指标**：

### 1. 既有服务端数据源（唯一权威事实源）
- **`GET /api/v1/statistics/report`**（`PeriodReport`）：`period`、`year`、`month`、`date_from`、`date_to`、`is_partial`、`cutoff_date`、`today`、`distance_m`、`activity_count`、`activity_days`、`duration_sum_seconds`、`known_duration_count`、`missing_duration_count`、`pace_eligible_count`、`pace_eligible_distance_m`、`avg_pace_seconds_per_km`。
- **`GET /api/v1/statistics/trends`**（`Trends.buckets[]`）：年度按 `month`（12 槽）、月度按 `week`（4–6 自然周槽，周一开始、首末周裁至月界），每桶均携带服务端聚合的 `distance_m`、`activity_count`、`activity_days`、`duration_sum_seconds`、`avg_pace_seconds_per_km`、`is_partial`。

### 2. 前端纯展示派生（不替代权威指标）
仅对上述已校验聚合做确定性呈现计算，并在实现中保留全部原始服务端数值与 `<details>` 表格：
- **峰值时段 & 峰值占比**：`max(bucket.distance_m)` 及其占 `report.distance_m` 比例（并列峰值保留并列提示）；
- **最快均配时段**：`min(bucket.avg_pace_seconds_per_km)`（仅从 `pace_eligible` 非空且里程 > 0 的服务端桶选取，不重算配速）；
- **持续活跃比例**：已到达时段中有跑步记录的桶数（如 `12/12 个月有开跑`、`5/5 周有开跑`）；
- **累计里程曲线**：对服务端分桶 `distance_m` 做前缀累加用于图形叠加；
- **体感换算参照**：单次均距（`distance_m / activity_count`）、等效全马场次（`distance_m / 42195`，延续现有 `route-poster-render.ts` 半马换算的传统）或 400m 标准跑道圈数（`distance_m / 400`）。

### 3. 严格不越界工作项 19（预留扩展位）
- **明确不纳入**：年度首跑、最长一跑、5K/10K 最佳成绩、探索城市、最常跑路线、足迹动画。
- **扩展位预留**：三个方向在页面结构末尾（海报区之前或之后）均可自然接入工作项 19 的独立叙事章节，本轮首发不渲染空占位卡、不拉取额外接口。

### 4. 9:16 分享图隐私白名单
- **严格只绘入**：通用品牌 `RunNote`、周期标题、日期范围与进行中截止日（`截至 MM.DD`）、服务端聚合总量（总里程、次数、天数、总用时、平均配速、覆盖注记）、无地理坐标的周期分布图形与参照换算。
- **严格禁止绘入**：姓名、昵称、用户名、邮箱、账户/活动 ID、活动标题与备注、轨迹坐标/形状、起终点、城市/地名、头像、身心健康数据、网址与可扫描二维码。
- **特别说明（方向 C 底部条码）**：方向 C 分享图底部的“里程指纹纹样”完全由 12 月 / 5 周的归一化里程比例决定柱高与柱宽，**不是** Code128/EAN 等可扫描编码，不含任何身份或时间序列编码信息。
- 预览弹窗继续保留「包含私人跑步记录的汇总」明确披露；全流程本机 Canvas 2D 渲染，0 外部网络请求。

## 三、三个重设计方向方案

三个方向在**空间骨架、图形隐喻、情绪气质、动效语言与 9:16 分享图版式**上彻底分化，而非同模板换色。

### 方向 A：「跑道年鉴 · Editorial Monolith」（推荐方向）

- **概念与情绪**：像一本只为你印制的《RunNote 年度/月度跑步特刊》——沉静、高级、有份量感，用极大与极小的排版反差、深森绿全出血英雄块和流畅的“里程地形”，把一年的奔跑定格为有收藏价值的出版物。
- **视觉语言与 Token 承接**：
  - 浅色主视觉突破普通白卡，采用深森绿渐变英雄面（源自 `--primary` 加深至 `#124e3d → #0b3529`）+ 极细暖黄（`--sport-yellow`）标准跑道等高弧线底纹 + 纯白超大等宽数字；深色模式自然融入 RunNote 暖炭灰系统（`#1e2421 → #151917` + `--primary` `#77d4ac` 薄荷绿巨型数字），全文继续沿用系统字体、`tabular-nums` 与 `400/500/600/700` 四档字重。
- **页面章节与信息节奏**：
  1. **特刊页眉**：返回个人记录 + 周期标题 + 进行中绿点状态徽标 + 精简周期分段/选择器 + 右上直达「生成分享图」。
  2. **01 · 里程巨碑（Editorial Monolith）**：非对称封面布局——左侧超大里程主数字（桌面 `clamp(3.6rem, 7.6vw, 6.4rem)`）、等效全马/单次均距事实行、峰值占比标尺条；右侧以极细发丝线排布四项核心服务端指标（次数、天数、总用时、平均配速）及统计覆盖注记。
  3. **02 · 里程地形与累计轨迹（Terrain & Cumulative Ribbon）**：放弃普通绿棍，采用 **SVG 平滑渐变面积地形 + 金色峰值锚柱 + 累计里程虚线** 双层图形。支持点击、悬停及键盘左右方向键逐月/逐周巡检，顶部胶囊实时联动展示该时段的四维服务端数据；下方折叠 `<details>` 完整无障碍数据表。
  4. **03 · 双联剖析（出勤节律矩阵 × 配速演进走势）**：左栏用 12 枚（年）/ 5 枚（月）同心进度环直观表达每期活跃天数与跑步次数；右栏采用反 Y 轴（越快越高）平滑折线与均值虚线标尺呈现配速变化，高亮最快均配期。
  5. **04 · 封存分享台**：页尾直接展示实时渲染的倾斜 9:16 迷你海报卡片，支持一键切换海报明暗预览或打开高清保存对话框。
- **月度 vs 年度适配**：年度呈现 12 月连续地形与 12 枚出勤环；月度自动切换为 4–6 自然周（`W1–W5`）地形曲线与周度出勤环，进行中周期的未到时段以虚点/低透明留空、不误读为零。
- **动效编排**：进场主数字 `easeOutExpo` 620ms 计数递增；地形主线 `stroke-dashoffset` 900ms 沿时间轴描边生长；峰值标尺宽度展开；切换周期或点击时段时局部高亮平滑切换；`prefers-reduced-motion` 下全部回退为瞬时静止呈现。
- **9:16 分享图（1080×1920）**：**「深森绿封面特刊」**——上半屏（0–820 px）全出血深森绿/暗炭情绪场承载巨型里程数字与标尺；下半屏（820–1920 px）切换暖纸白/暖炭灰卡片，嵌入平滑渐变里程地形曲线与金色峰值点、2×2 编辑部指标卡与刊尾注记。

### 方向 B：「环道计时仪 · Stadium Telemetry」

- **概念与情绪**：把跑步最核心的物理符号——**400 米标准田径跑道与精密运动计时码表**——抽象为整套数据图形与仪表语言。锐利、精准、富有速度与竞技成就感。
- **视觉语言与 Token 承接**：以精密环形刻度、等宽字标、左边缘运动色锚条（承接 `--primary`、`--sport-green`、`--sport-blue`、`--sport-yellow`）构筑专业运动仪表盘气质；深色模式宛如夜场体育场泛光灯下的精准计时器。
- **页面章节与信息节奏**：
  1. **顶栏计时状态条**：带呼吸状态灯的 `LIVE / SEALED` 等宽状态行 + 周期切换 + 「生成环道海报」。
  2. **主舞台 · 环道总览仪 + 计时码表板**：左右双栏——左侧为可交互 **SVG 环道表盘**（**年度**：12 个月份沿 12 点钟表盘放射排布，半径编码里程、峰值月点亮赛场金；**月度**：4–5 周化为 4–5 条嵌套同心跑道弧并排冲刺），点击任意扇区/跑道即在表盘中心切换展示该时段详情；右侧为 2×2 计时码表读数格 + 400m 等效圈数徽章 + 周期配速区间卡尺条。
  3. **分段成绩单（Split Telemetry）**：把 12 月或 5 周排成类似马拉松分段成绩单的横向条带，每行同时呈现里程进度条、跑步次数/天数、均配速，并用金/蓝双圆点标注峰值与最快均配；点击行与表盘双向联动。底部附 `<details>` 数据表。
  4. **环道完赛海报条**：一键预览与导出 9:16 中心环道徽章海报。
- **动效编排**：环道扇区/同心跑道缩放扫入；进行中状态灯柔和脉动；点击扇区时其余扇区降不透明度聚焦当前时段，表盘中心读数实时刷新。
- **9:16 分享图（1080×1920）**：**「环道完赛纪念牌」**——画面正中以直径 824 px 的超大精密环道表盘（年度 12 月放射环 / 月度 5 跑道同心环）作为绝对视觉图腾，圆心嵌入超大总里程数字，下方串联峰值/最快均配胶囊与 2×2 运动色锚指标格，在信息流缩略图中辨识度极高。

### 方向 C：「奔跑存根 · Tactile Runner's Receipt & Zine」

- **概念与情绪**：温暖、有手工温度、轻盈好玩且自带社交传播基因。直接延展 RunNote 现有单活动海报中颇具口碑的「跑步票根（`poster-ticket.png`）」视觉血统，升级为**三联撕口热敏票据与打孔手账**。
- **视觉语言与 Token 承接**：浅色使用暖米白纸底（`#fcfcf7`）、经典 RunNote 亮黄票头（`--sport-yellow`）、半圆撕口缺口、虚线裁切线与倾斜圆形邮戳印章；深色转化为复古“暗室黑卡纸”（`#312f2c` + 薄荷绿油墨与烫金峰值）。零外部图片纹理，全部由纯 CSS/SVG/Canvas 几何实现。
- **页面章节与信息节奏**：
  1. **桌面双栏「存根工坊」布局**（手机合为连贯长票据）：左侧吸顶栏实时展示倾斜的 **9:16 立体迷你存根**，随周期与纸色即时更新，强化“所见即所分享”的即时欲望；右侧是三联撕口长卷：
  2. **第一联 · 里程核销单**：亮黄票头 + 巨号核销里程 + 倾斜圆形完赛章（如 `SEALED · 12/12 MONTHS`）+ 经典点线对齐（`跑步次数 ········ 132 次`）四项指标账单。
  3. **第二联 · 节律打孔带（Punch-Card Matrix）**：独特的复古打孔卡柱阵，每期由堆叠方格组成里程高度，峰值列以金黄色整列点亮；点击任意列在下方弹出单期“微回执明细”。
  4. **第三联 · 分段配速回执与里程指纹**：紧凑斑马纹回执清单 + 由分期里程比例生成的纯装饰性几何条码纹样 + `<details>` 完整无障碍数据表。
- **动效编排**：票据整体以轻微纵向下拉回弹模拟热敏机“出票”（`480ms`）；完赛圆章在主数字落定后延迟 `220ms` 轻盖入位；打孔列点击即时高亮反馈。
- **9:16 分享图（1080×1920）**：**「珍藏版锯齿长票根」**——整张 1080×1920 画面呈现带底部锯齿边、双侧半圆撕口、三联虚线裁切、倾斜完赛印章、打孔卡矩阵、点线对齐账单与里程指纹底纹的完整实体票据，朋友圈与小红书的“晒图冲动”最强。

## 四、横向对比与推荐结论

| 对比维度 | 当前线上 v1.3.0 | **方向 A · 跑道年鉴（推荐）** | 方向 B · 环道计时仪 | 方向 C · 奔跑存根 |
| --- | --- | --- | --- | --- |
| **视觉记忆点** | 弱（普通双白/黄卡片） | **高（深森绿全出血巨碑 + 渐变地形）** | **极高（中心环道表盘图腾）** | **极高（实体锯齿票根 + 打孔卡）** |
| **与 RunNote 主站气质契合度** | 高但过于平淡 | **最高（自然延伸暖纸 + 品牌绿 + 暖炭灰）** | 高（偏硬核训练/赛事仪表感） | 中高（手账/出版物风格，略带玩味） |
| **既有数据利用率** | 低（仅 1 维里程柱） | **极高（里程地形 + 累计 + 出勤环 + 配速曲线）** | **极高（环道里程 + 圈数 + 配速卡尺 + 分段单）** | 高（核销单 + 打孔带 + 配速回执） |
| **390px 窄屏与长数字稳健度** | 稳健 | **最稳健（纵排节奏自然，地形与表格零挤压）** | 良好（环道缩小后 12 月字标需精控字号） | 良好（12 列打孔卡在 320px 需适当收窄间距） |
| **工作项 19（年度故事）扩展性** | 一般 | **最佳（按 01/02/03 杂志章节顺延无缝插入）** | 良好（可扩为独立战报卡，但偏离仪表主题） | 良好（可续印第四联撕口，但单票过长） |
| **Canvas 2D 实现复杂度** | 极低（87 行） | **中（贝塞尔地形 + 渐变面，约 220 行）** | 中高（极坐标扇区 + 同心弧 + 文字避让，约 240 行） | 中（锯齿路径 + 旋转印章 + 打孔块，约 250 行） |
| **社交分享欲望** | 低 | **高（高级感强、男女跑者通吃）** | **高（极客/严肃跑者极爱）** | **极高（小红书/朋友圈晒图感最强）** |

### 推荐建议：主推「方向 A 页面」+ 可选「多版式 9:16 分享图」

1. **回顾页主方案推荐方向 A（跑道年鉴）**：
   - 既彻底摆脱“后台报表卡片”的简陋感，又与 RunNote 整体的克制、温暖、数据优先的审美完全同频；
   - 杂志章节结构（01 巨碑 → 02 地形 → 03 出勤与配速 → 04 分享台）天然为后续**工作项 19（年度故事）**留出最顺滑的插槽，届时直接作为 Chapter 04 插入即可，无需二次重构；
   - 在 1440×900 桌面首屏即可完整呈现深森绿巨碑英雄区与地形曲线上半部，视觉张力立现；在 390×844 手机端阅读节奏最舒展。
2. **分享图的高性价比进阶选项（供拍板）**：
   - RunNote 现有 `route-poster-render.ts` 已具备 `posterStyles` 多版式切换交互范式；
   - 如果负责人既想要方向 A 页面沉稳耐看，又舍不得方向 B 的“环道徽章海报”或方向 C 的“珍藏票根海报”，可以在「生成分享图」对话框里直接提供 **3 款 9:16 分享图版式切换（特刊 / 环道 / 存根）**——全部消费同一份白名单 `Recap` 对象、纯前端 Canvas 2D 零后端成本，让用户在分享那一刻拥有极高的自由度与惊喜感。

## 五、响应式、可访问性、性能与实现风险评估

### 1. 响应式与明暗主题
- **桌面 1440×900**：保留既有 `≥800px` 悬浮顶部条留白；三个方向首屏均能直观呈现核心大数字、主图形与分享入口，无横向溢出。
- **手机 390×844（及 320px 兜底）**：周期切换与主操作按钮满足 ≥44 px 触控高度；长数字使用 `tabular-nums` + `clamp()` 自适应缩字；窄屏下辅助提示与次级列自动收敛，`<details>` 完整数据表局部可横向滚动并附 `role="region"` 与中文 `aria-label`。
- **明暗外观**：严格复用 `app.css` 的 `--background`、`--surface`、`--foreground`、`--muted-foreground`、`--primary`、`--border`、`--header-tint` 与暖炭灰深色基调（`#292725` / `#33312f`），仅在回顾页局部引入可纳入语义令牌的深森绿英雄面（`--recap-forest`）与暖纸表面（`--recap-paper`）。

### 2. 可访问性与边界态
- 所有指标采用语义 `<dl>/<dt>/<dd>`，缺失值渲染 `—` 并附 `.sr-only` 说明；峰值与最快均配除颜色外均提供文字标签与图标/星标双重提示；
- 交互图表节点均具备 `tabindex="0"`、`role="button"`、`aria-pressed` 与完整中文 `aria-label`，支持键盘遍历；
- `<dialog>` 保留原生 top-layer、Escape 关闭与关闭后焦点返回触发按钮；
- `prefers-reduced-motion: reduce` 下所有进场动画、数字递增与描边生长均自动禁用；
- 空周期、部分计时缺失（如原型内置的 `2026 年进行中` 样例，含 `用时覆盖 112/114 次 · 配速覆盖 110/114 次` 与 `12 月未到`）、趋势请求失败重试均沿用现有状态机，不破坏既有容错。

### 3. 性能与工程改动面
- **零重型依赖**：三个方向的页面图形均用轻量内联 SVG/CSS，分享图用纯 Canvas 2D 按需动态导入（不引入 ECharts、html2canvas、外部字体或位图素材），首屏额外包体增量预计 `< 15 KB gzip`。
- **预期改动文件范围（获批实施后）**：
  - `frontend/src/lib/recap.ts`：保留原字段兼容，扩展分桶的 `activity_count`、`activity_days`、`duration_sum_seconds`、`avg_pace_seconds_per_km` 与展示派生 helper；
  - `frontend/src/routes/workspace/records/recap/+page.svelte`：升级为获批方向的章节结构；
  - `frontend/src/lib/components/RecapDistribution.svelte`（及视方向拆出的 1–2 个纯展示子组件）；
  - `frontend/src/lib/components/RecapShare.svelte` 与 `frontend/src/lib/share/recap-render.ts`：落地新版 1080×1920 Canvas 2D 排版（以及可选多版式切换）；
  - 对应单元测试与 `playwright.recap.config.ts` 视觉回归更新。
- **主要风险与缓释**：
  1. **中英文与超大里程（如 `12,345.6 km`）在 Canvas 2D 溢出**：延续 `measureText` 动态缩字保护，并在测试夹具补极端大值用例；
  2. **仅 1 个有效桶（例如 1 月 2 日刚跑一次）的曲线退化**：当有效桶 `< 2` 时，地形曲线/配速折线优雅降级为单点锚柱或提示文字，不出现 NaN 坐标；
  3. **深森绿局部英雄面在 forced-colors 模式下的可读性**：通过 `@media (forced-colors: active)` 回退系统高对比色与实线边框；
  4. **低端手机首次生成 1080×1920 PNG 耗时**：保持与现有相同的“点击才渲染、关闭即释放 Object URL、单次只保一份”策略，并在实装后以真机基线验收。

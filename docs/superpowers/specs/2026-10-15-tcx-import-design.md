# TCX 导入设计

状态：用户已确认，代码和隔离测试验收已完成；2026-10-15 经用户另行授权，开发库已升级到 0007_tcx_imports，后端已启动且就绪。

## 样本与已确认事实

分析文件为用户提供的 `20261004Outdoor running.tcx`，来自 Mi Fitness，原文 222,187 字节。包含一次活动、一个 Lap、1,163 个 GPS 点，每个点均有坐标和时间。`Sport` 为空，没有海拔、逐点心率或逐点步频。

用户确认实际运动时间为 2026 年 10 月 4 日下午，`HeartRateBpm=156` 为平均心率。因此本次样本按导出时间误标 UTC 处理：原文 `2026-10-04T16:15:20.000Z` 应解释为北京时间 `2026-10-04 16:15:20+08:00`，结束时间为同日 `16:37:22+08:00`，活动日期为 `2026-10-04`。原文保留不改写。

设备汇总为距离 2,999 米、用时 1,166 秒（19:26）、热量 144 kcal、平均心率 156 bpm、步数 3,262。首末点经过时间为 1,322 秒（22:02），与设备用时相差 156 秒；文件未明确声明暂停，不能把差值确认为暂停时长。

## 推荐方案与范围

推荐原生解析 TCX，输出现有轨迹处理所需的点和段，复用清洗、地图、认证及事务保存逻辑，同时单独保存设备汇总。与先转换为 GPX 相比，可以保留心率、步数、热量、设备距离及用时；与另建完整活动和地图流程相比，可保持已有活动、统计及隐私行为一致。

首版围绕本次带 GPS 的单活动跑步样本完成。支持同一活动的多个 Lap/Track 并保留分段，不将不同 Track 跨边连接；多活动文件提示拆分后上传。完全无 GPS 的室内活动另行定义指标和质量规则，不在本设计中直接作为普通轨迹导入。

## 字段映射与指标口径

| 来源 | 存储或用途 | 样本结果 |
| --- | --- | --- |
| 上传原文、文件名 | 独立 TCX 来源记录，保存原始字节与哈希 | 原文不修改 |
| 修正后的首末 Trackpoint/Time | `started_at`、`ended_at`、`activity_date` | 10 月 4 日 16:15:20 至 16:37:22，北京时间 |
| 首末点时间差 | 现有 `elapsed_seconds` | 1,322 秒，保持“经过时间”含义 |
| Lap/TotalTimeSeconds | 新增可空 `timer_seconds` | 1,166 秒，显示为设备用时 |
| Lap/DistanceMeters | 现有 `distance_m`，并标记设备汇总来源 | 2,999 米 |
| 设备用时 / 设备距离 | `avg_pace_seconds_per_km` | 约 6 分 29 秒 / km |
| Lap/Calories | 新增可空 `calories_kcal` | 144 |
| Lap/HeartRateBpm，Mi Fitness 样本约定 | 新增可空 `avg_heart_rate_bpm` | 156 |
| Lap/Steps | 新增可空 `steps` | 3,262 |
| Trackpoint/Position 与 Time | 复用轨迹点、分段存储 | 1,163 个源点 |
| 轨迹清洗后的距离 | TCX 来源记录中的派生指标 | 供核对，不覆盖有效设备距离 |

设备汇总缺失时，距离和用时回退到可信的轨迹计算；非法设备数值返回明确错误，不能以静默回退掩盖异常。多 Lap 的距离、用时、热量和步数只有各 Lap 都有对应有效字段时才形成完整汇总；单 Lap 有有效平均心率时直接保留，不要求同时存在设备用时；多个 Lap 仅在各 Lap 平均心率及正设备用时完整时按用时加权，否则不声称有全程平均心率。

样本直接以文本存储 `HeartRateBpm`，需要专门兼容；标准 TCX 的 `AverageHeartRateBpm/Value` 应独立支持，不把 `MaximumHeartRateBpm` 或所有导出器的直接心率字段一律解释为平均心率。

## 时间解释

导入入口增加“时间解释”选项，默认遵守文件时区。对误标 UTC 的文件，用户可明确选择“按所选时区的当地时间解释”，使用账户时区或手动指定时区。此样本选择后按 Asia/Shanghai 的 16:15 解释，统一应用到活动及所有轨迹点时间。

不通过文件名、创建者或所有 `Z` 后缀自动猜测时区错误。记录实际采用的时间解释和时区，确保可追溯。补录日期不能替代时间修正；修正完成后再执行现有日期冲突检查。夏令时重复或不存在的当地时间应明确拒绝并提示更换解释方式，不能猜测偏移。

## 数据库与 API

增加 `0007_tcx_imports` 迁移：扩展 `activities.source` 允许 `tcx`，增加上述可空设备汇总字段及有限、非负等合理约束，新增 `tcx_imports` 来源表，保留原文、归属、哈希、解析版本、时间解释、设备摘要与轨迹派生距离。旧 GPX、手动活动的新字段为空，既有记录不重新计算。数据库迁移仅在隔离测试库验证，开发库是否执行迁移另由用户授权。

增加 `/api/v1/tcx-imports`，复用单文件、CSRF、owner 校验、解析后重新验证身份、按用户串行导入、原子保存与数据版本递增的现有约定。来源表使用活动与用户的复合归属约束，并随活动删除。

重复检测至少保证同用户同原文不能重复保存，且不同时间解释不能绕过原文重复检测。轨迹规范化哈希需基于实际解释后的时间，与 GPX 的比对仅在点、时间和分段完全等价时成立；不承诺识别所有跨格式的同次运动。重复时仅返回当前用户已有活动链接。

列表、详情、统计及本地 AI 统计快照的运动用时采用 `timer_seconds` 存在则优先，否则采用 `elapsed_seconds`；聚合配速使用同一用时口径和距离计算。有效设备用时不依赖轨迹时间完整性；轨迹时间缺失、非法或首末相同时，仍可用有效设备汇总计算配速，同时保留轨迹质量提示。无设备用时时，配速仍要求舍入后的经过时间大于零。详情同时显示设备用时和经过时间，避免混淆。现有 GPX 行为保持原计算口径。AI 供应商仍仅接收已有允许的聚合字段，本次不自动增加原文、GPS 或心率等私密数据。

私人活动 API 增加可空设备汇总字段。公开及分享 API 保持既有白名单，不自动公开新心率、步数、热量或原文；既有 elapsed_seconds 响应字段优先采用设备用时，以与公开配速保持一致。新增字段和解析信息仅用于私人活动详情。

## 错误处理与验收

TCX 使用禁止 DTD、实体及外部资源的 XML 解析；不访问 schemaLocation，不读取 XML 内路径或 URL。沿用单文件 10 MiB、50,000 个源点、1,000 个源段及隔离解析超时保护，并把请求体大小保护覆盖到 TCX。

验收使用脱敏合成 fixture，不将用户真实 GPS 文件提交到仓库。覆盖该 Mi Fitness 结构、标准平均心率结构、普通 UTC 与当地时间解释、跨日日期、Lap 分段、设备与轨迹指标分离、缺失与非法汇总、重复导入、owner 隔离、CSRF、解析限制和失败不产生半成品。运行后端相关单元与隔离数据库集成测试、前端检查与构建，并在真实浏览器验证桌面及手机导入、错误恢复和详情指标。

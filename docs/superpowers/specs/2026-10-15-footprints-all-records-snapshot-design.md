# 个人足迹全量记录与自动整合快照设计

日期：2026-10-15。状态：用户已确认实施；代码及隔离验证完成，开发环境尚未应用。

## 需求与使用方式

- 个人足迹的「轨迹叠加」「运动热力图」统一展示本人的全部运动记录，移除年份、日期范围和应用筛选。
- 无轨迹记录计入总记录数，但不凭空生成路线；地图另显示有可展示轨迹的记录数。
- 导入 GPX、TCX、小米运动数据后自动更新整合结果，无需用户逐次生成。
- 页面显示「全部记录」和最近生成时间；生成中显示明确状态，完成后自动读取。
- 建议默认后台每 60 秒检查变更，每 24 小时刷新一次整合快照。刷新周期从后台生成时间起算，不要求页面一直打开。
- 「删除老旧整合记录」指清理派生缓存与被替换的快照，绝不删除原始运动记录或导入文件。

## 实施前确认的行为

- `frontend/src/routes/footprints/+page.svelte` 默认选择用户时区当年；切换地图模式会再次请求后端。
- `frontend/src/lib/api/footprints.ts` 将年份或日期范围转换成 `date_from/date_to` 查询参数。
- `backend/app/modules/footprints/service.py` 每次查询原始段；热力模式执行完整边与固定网格相交，并按活动去重。
- 当前实时查询有 250000 点、10000 段及热区候选/输出上限，不能仅扩大日期范围就宣称支持全量历史。
- GPX/TCX、小米导入以及活动编辑、单条/批量删除已有 `activity_data_version` 递增，可复用为变更信号。
- 目前没有足迹快照表或常驻汇总任务；`main.py` lifespan 只管理引擎释放。
- 足迹 router、main、模型注册、导入模块与测试夹具已有用户未提交改动，实施时在现有内容上追加必要变更。

## 方案比较

1. **推荐：单活动派生缓存 + 每用户完整快照。** 新记录只计算自己的路线展示几何和热区，后台组合全部缓存；页面直接读取持久化结果。需要两张派生表和后台任务，但避免每次访问及每次导入重算全部历史空间相交。
2. 每用户快照、每次变化全量重算。表结构较少，但导入越多，后台重复计算历史的成本越高。
3. 进程内缓存。改动小，但重启丢失、多进程不一致，也无法可靠清理和自动恢复，不适合本需求。

## 持久化与生成流程

新增两类私有派生数据，实施时核对后采用迁移 `0010_footprint_snapshots`。

- 单活动缓存：UUID 主键、`user_id`、唯一 `activity_id`、算法版本、展示几何、去重后的网格坐标、不可展示段统计、生成时间。活动和用户均以外键级联删除；使用活动/用户联合约束防止归属错配。
- 用户快照：UUID 主键、唯一 `user_id`、源 `activity_data_version`、算法版本、生成时间、两种模式的完整 GeoJSON 与统计。一个用户只保留一个成功版本，两种模式在同一次发布中更新。
- 活动标题、日期等元信息在组合快照时从本人活动读取；既有路线不可编辑，因此仅新增活动或算法版本变化需要重新计算单活动空间缓存。将来若引入路线修改，必须同时失效对应缓存。
- 工作进度与失败重试信息持久化到用户快照的独立状态字段；保留成功数据的版本与时间，不把失败时间伪装成生成时间。

生成顺序：

1. 后台发现用户没有成功快照、源版本改变、算法版本变化或成功快照超过 24 小时。
2. 使用独立于导入互斥锁的 PostgreSQL 足迹任务 advisory lock，避免多进程对同一用户重复构建；不修改既有每用户导入互斥机制。
3. 在独立 Session 中记录源版本，按活动分批生成缺失的派生缓存；复用现有日期变更线、极区裁剪、单点、零长度及多段语义。
4. 从全部活动缓存组合路线；热区按活动内已去重的网格累加，每个活动每格最多贡献 1。无轨迹活动也包含在总数中。
5. 计算期间不持有 users 行锁。发布阶段短暂锁住本人 users 行并再次核对源版本；版本变化则放弃此次发布，重试最新版本。
6. 两种模式的完整结果与成功元数据在同一事务原子替换；失败不发布半成品、不标记成功。

原来的账户级 25 万点上限不用于新快照入口；空间计算按活动执行。单任务仍需超时、候选网格和资源保护，超限明确显示生成失败，不能只保留前 N 条记录或静默截断。全量 GeoJSON 仍有传输和浏览器绘制成本，需要单独测量，不能把数据库缓存等同于无限容量。

## 后台任务、刷新与清理

- 由 FastAPI lifespan 启停轻量后台循环，不引入 Redis、Celery、容器或额外服务。
- 周期扫描是可靠触发源，已提交导入即使遇到进程重启也会被再次发现；预计在提交后下一次扫描开始更新，不延长导入请求去完成全部历史整合。
- 同步数据库与空间计算在线程中执行，独立 Session，不复用请求 Session，不阻塞 asyncio 事件循环。
- 每个进程限制同时一个构建任务，跨进程通过数据库任务锁去重；按有限批次轮转用户，失败采用退避，避免一个异常用户阻塞其他用户。
- 24 小时刷新优先复用单活动缓存；算法升级才重算对应空间派生结果。
- 成功发布直接覆盖该用户旧快照，不累积历史快照；活动删除时级联删除自己的单活动缓存，算法旧版缓存由后台分批替换/清理。
- 定期失败可继续提供源版本仍一致的上次成功结果，并显示更新时间及刷新失败；源版本不一致时绝不返回旧数据。
- 停止时终止领取新任务，等待有界的在途事务结束并释放连接，再 dispose 引擎。数据库 revision 不匹配时不执行派生写入，等升级并 ready 后恢复。

## 接口与隐私

- 新增本人只读 `GET /api/v1/footprints/all?mode=tracks|heatmap`，使用既有认证、响应信封及明确响应 schema；拒绝未知参数。
- 保留现有带日期范围的 `/api/v1/footprints` 与 `/provinces` 的接口和行为，避免影响既有调用方与首页省份墙。
- 新响应包含 `status`（pending/ready/failed）、成功生成时间、当前是否正在刷新、`refresh_failed` 及选中模式的数据；GeoJSON 仅在成功源版本匹配当前用户版本时返回。
- 全量响应明确 `scope=all`；不伪造年份日期范围。无记录时返回 ready 的空集合。
- 所有读取与写入按本人过滤；匿名 401、不能指定他人 owner。响应与 SSR 代理继续 `no-store`，不扩大代理请求头白名单。
- 导入、修改、删除提交后版本不一致的快照立即不可读；重建完成前显示「足迹正在更新」。尤其不能继续展示已删除路线或旧标题。
- 不在 GET 请求中直接执行空间重建；页面生成中最多每 5 秒轮询状态，完成、失败、401、页面卸载后停止。普通 ready 页面不持续轮询。
- 快照包含私人轨迹，只保存在本地 PostgreSQL 与本人浏览器；不进入公开接口、AI 请求、日志或仓库。
- 原始轨迹、详情指标、可见性、分享、CSRF 与现有导入防重复语义保持不变。

## 前端变更

- 删除足迹页面的日期筛选及相关状态，URL 只保留 `mode`；旧年份/范围链接进入时统一展示全部记录。
- 展示全量记录总数、地图可展示记录数、生成时间和生成/失败状态，错误提示不再要求缩小日期范围。
- 新响应由 `lib/api` 逐字段校验，包含状态、时间、数量、模式与 GeoJSON；更新地图类型以支持全量数据，兼容保留的原有接口类型。
- 保留请求令牌、AbortController，补齐 disposed 清理；401 清空私有数据并跳转登录。
- 保留地图交互、详情入口、底图关闭/失败兜底、热区图例、完整数据表和明暗主题订阅。
- 同步更新合成 API 与足迹 UI 测试，不把合成 UI 通过当成真实数据库验收。

## 验证计划

- 后端单元：状态机、周期、失败退避、版本检查、关闭流程和迁移防御性降级。
- 独立 PostGIS `_test` 库：两用户隔离，跨年份全部记录，三种导入自动生成，单条/批量删除，标题更新，空记录，重启补建，多 worker 去重，构建期间导入/删除竞争，原子发布及旧结果清理。
- 空间回归：采样密度不影响热度、同活动绕圈/多段去重、不同活动累加、段间不连线、日期变更线、极区、单点与零长度；与现有实时计算结果对照。
- 性能：合成超过 25 万点的多活动历史；证明正常全量读不再访问原始点/段执行空间相交，重复读取查询数不随活动数增长；新导入只生成缺失单活动缓存。记录实测响应大小、耗时与绘制时间，不预报性能数字。

- 前端执行 `pnpm check`、相关 Vitest、相关 UI、生产构建；后端执行相关 pytest、Ruff 与格式检查。集成库不可用时明确 BLOCKED/未验证，不把 skip 当通过。

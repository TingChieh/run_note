# RunNote V1.3-A 轨迹性能分析与优化报告

日期：2026-10-14。验收对象：`main` 的 HEAD `9e59c2c` 加既有 V1.1/V1.2 未提交工作区及本轮改动。本轮未提交、推送或部署。

## 结论

**PASS：常规大轨迹展示的主要瓶颈已定位并完成小范围优化。** 相同 100 条 × 1,000 点合成 GPX 的最终配对 HTTP 中位数 **1,349.31 → 248.97 ms（下降 81.5%）**；正文 **5,559,185 → 2,692,114 B（减少 51.6%）**。全部源点仍保留，没有简化轨迹或改变距离/时长/配速算法。

瓶颈并非缺索引：原实现把 99,900 条原始边逐一裁剪、投影，再输出重复端点；Python 通用编码和前端展开/复制坐标进一步放大开销。常规轨迹改为读取有序整段，异常轨迹仍逐边处理，前端改为原位遍历求边界并复用无需平移的几何。

**热力图性能未取得实质改善**：10 万点仍约 1 秒。V1.2 那次独立空间 SQL 的 5 秒超时，本轮单用户串行未重现；不能声称已找出该历史失败的唯一原因或完全消除生产超时。额外四并发复现了另一个真实超时：认证用户行锁等待达到 3 秒，原版 3/12 返回 500；轨迹优化后 12/12 成功，但认证串行机制仍在，热图/异常轨迹排队风险保留。

## 数据与测量方法

主场景是 **100 个真实导入活动 × 每条 1,000 源点 = 100,000 点**，每条围绕 31.2/121.4 的合成重复绕圈，记录相隔一天，日期在 2025 年。单文件上限 50,000 点，未通过放宽上限导入一个 100,000 点文件。另经真实接口导入 2023 年 100 点和 2024 年 50,000 点各一条；以独立日期范围测试它们及 2025 年第一条 1,000 点。

最终配对测量先运行保存的原实现，再运行优化实现，使用同一数据库、相同 owner、日期、源数据和本机端口；此时没有并行构建/自动化测试。每规模/模式串行 3 次，逐次落盘。最早基线与第一轮优化也保留，其 HTTP 10 万点中位数为 1,580.39 / 258.96 ms；最终表使用后续配对样本，不挑最快值。原工作区性能源码副本用于切换基线，只加载在忽略的测试启动器中。

- SQLAlchemy cursor 事件记录 **execute 到驱动返回**，其中含 PostgreSQL 执行和结果字节返回；`.mappings().all()` 单独计结果 JSON 解码/取行。服务总耗时减去这两个阶段得到 Python feature 组装及其他调用开销。它不是纯数据库 CPU 时间。
- 真正的 PostgreSQL 时间另用 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`；空间阶段、读几何及预计算几何的 ST_AsGeoJSON 单独运行。临时表只用于拆解测量，已在事务内删除，不是产品缓存。
- FastAPI 测试进程注入 Server-Timing：service、SQL、通用响应编码、JSONResponse.render 和 response-start；未将探针加入产品。HTTP 首字节/正文从真实构建代理的流式请求测量。server 到首字节差值包含代理、调度、loopback 等，不能解读为纯网络时间。
- 内存单独测：tracemalloc 仅捕获服务 Python 分配；全响应链路用两个独立新进程的 RSS/ru_maxrss。带内存探针耗时不用于主表。
- 浏览器实际登录，390/1440 两视口 × 两模式 × 3 次。临时 Performance 标记记录正文读取解析、响应校验、世界副本坐标转换、MapLibre addSource 到首次 source-loaded render；另采 Long Tasks/CDP JS 堆。最终源码已恢复无探针并重新构建、验证。

各阶段的独立查询、不同请求或各自中位数 **不能相加当成某一次 HTTP 的精确时间线**。样本为本机热缓存、未固定全机负载、无生产带宽/延迟限制；不是容量 SLO、p95/p99 或低端手机/GPU 验收。

## 主要瓶颈证据与索引

原空间 CTE 的 projected 节点实际产生 **99,900 行**，ST_DumpSegments 每条执行一次、ST_Dump 每条边执行一次；独立空间阶段 **597.021 ms**，原 tracks 完整 EXPLAIN **651.195 ms**。数据筛选/计数查询 **0.798 ms**；没有证据把超时归因于没有空间索引。

现有索引：activities `(user_id, activity_date DESC, id DESC)`；segments `(activity_id)` 及唯一 `(activity_id, segment_index)`；points 主键 `(segment_id, point_index)`；segments geom GiST。单点 fallback 使用 points 主键；详情首末点使用有序主键访问。小表的 owner/date 查询选择顺序扫描/哈希连接是合理计划，不能仅凭 Seq Scan 判定缺索引。优化后计数查询 EXPLAIN 0.734 ms，tracks 为 **9.934 ms**；常规轨迹不再调用逐边投影路径。

GiST 无法加速“已按 owner/date 选出的每条边都做空间变换”的全量运算；本接口也没有空间 bbox 检索谓词。故本轮 **没有新增索引或数据库迁移**。真实大库中其他 owner 数量、日期选择率和统计信息仍需在目标环境复核，本机计划不代表所有生产数据分布。

拆解实验：热缓存“读取并计算全部源几何内存尺寸”中位数为原 0.237 / 新 0.216 ms（原首样本 24.418 ms，保留冷启动差异）；对已预计算的两类几何单独 ST_AsGeoJSON 原 **9.525** / 新 **4.129 ms**。这些数据进一步说明空间逐边处理比纯 GeoJSON 文本格式化更贵；后者不是 651 ms SQL 的全部来源。

## 采用的改动

1. **常规展示整段读取**：owner/date 过滤保持在共同 selected CTE。仅当该段经度 bbox 跨度 ≤180°、所有纬度均处于 Mercator 支持范围时，直接输出存储的有序 LineString（9 位小数，与旧足迹响应精度一致）。保留所有 bends、重复采样、绕圈顺序和 segment_index；零长度整段以 Point 显示，单点仍使用原 fallback。
2. **异常轨迹回退**：经度跨度大或越过极区的段仍逐边、跨日期线拆开、平移、裁剪、投影，保持段之间不连接。没有把所有轨迹错误地当一条连续线。
3. **前端原位遍历**：新增 forEachCoordinate/geometryBounds，求 anchor 不再展开全部点，求 bounds 不再生成整份临时坐标数组；复用 derived display/bounds。offset=0 的几何直接复用，需平移的 piece 创建新坐标，不修改服务原数据。MapLibre source 使用新 feature/properties，不改输入统计。
4. **边界缺陷修复**：本机 ST_Split 对合成水平线 `179.999 → -179.999` 返回未分离的三点线，后续 envelope 裁剪只保留东侧。改为对 shift 后的边分别与 [0,180] / [180,360] envelope 相交并 collect，再各自 wrap；轨迹和热图恢复东西两侧覆盖。网格定义、完整边相交和 distinct_activity_per_cell 统计定义未变。**该错误样本的热图输出有意修正，不能宣称所有历史错误结果逐字不变。**

未采用：轨迹简化、多缩放精度、缓存、任务队列、调高限制/超时、认证锁弱化、新依赖。MapLibre/ECharts 继续原有按页面动态加载；常规轨迹的整段路径已取得主要收益，暂不引入精度参数或异步工作流。

本轮生产代码改动仅 `backend/app/modules/footprints/service.py`、`frontend/src/lib/api/footprints.ts` 和既有 `FootprintMap.svelte`；两个既有测试文件新增回归。FootprintMap 的原 UI 改造按工作区副本保护，未覆盖用户已有设计。
